      Your numbers right now

      1. Where the numbers come from

      There are three sources. Each one answers a different question.

      • GitHub quota (exact). The dashboard asks GitHub's copilot_internal/user endpoint, using your gh login token (or TOKEN_MONITOR_GH_TOKEN). From the answer it keeps only premium_interactions: the entitlement (your budget), remaining (spent = entitlement − remaining), the quota reset date, and the plan name. Nothing else is stored.
      • OpenCode's local database (estimate). It is opened read-only. For each assistant message it reads the model, the token counts and the cost OpenCode wrote down. This works offline and gives the per-day, per-hour and per-model views.
      • History snapshots (exact, but sparse). Each time the quota is fetched and has changed, one line (time, spent, budget, period end) is added to .token-monitor/history.jsonl. Daily costs and the calibration are built from these.

      An organisation budget portal's own figure is not used: such portals usually sit behind single sign-on, which a script can't use. What you see is your personal seat quota from GitHub. If the portal shows a different budget, that is why.

      2. Budget, spent, left and % used

      GitHub reports credits. The dashboard shows dollars by dividing by TOKEN_MONITOR_CREDITS_PER_USD (default 100; set it to 0 to see raw credits). History and --json keep the raw credits.

      ItemHowExample
      Budgetentitlement ÷ 10030,000 cr ÷ 100 = $300
      Spent(entitlement − remaining) ÷ 100(30,000 − 21,600) cr ÷ 100 = $84
      Leftbudget − spent (never below 0)$300 − $84 = $216 (21,600 cr)
      % usedspent ÷ budget84 ÷ 300 = 28%

      The gauge turns amber at 70% and red at 90%. The period runs from one month before the reset date to the reset date.

      Budget override gotcha. TOKEN_MONITOR_BUDGET (or the Settings box) is in dollars, not credits. Typing 400 means a $400 limit (40,000 credits). Typing 30000 means $30,000, and every percentage will look tiny. The override only changes the limit: spent still comes from GitHub, and "left", % used and the "lasts until" line are all recalculated from your number. Clear it to go back to GitHub's value.

      3. Daily cost

      GitHub only gives a running total, not a per-day figure. So the dashboard looks at how much that total grew between two snapshots, and shares the growth over the days in between, in proportion to the local cost of the messages on each day (or evenly by time if there were none).

      Example. Monday 22:00 the quota reads 8,000 cr. Tuesday 22:00 it reads 8,350 cr, so the real growth is 350 cr = $3.50. OpenCode logged $0.50 of messages on Monday and $1.50 on Tuesday. Monday gets 3.50 × 0.25 = $0.88, Tuesday gets 3.50 × 0.75 = $2.63.

      Days or messages that fall outside every snapshot interval (before the first snapshot, between billing periods, or since the last snapshot) use the local estimate instead, scaled by the calibration factor. In the cost chart, the bright blue part is portal spend and the muted blue part is local estimate. Snapshots are only taken while something is fetching (the dashboard open, or the CLI), so a long gap gives coarser days.

      The 24h and 72h ranges are always local estimates: portal spend is too sparse to split by hour.

      4. Local cost per message

      OpenCode works out a dollar cost for every message from the model's price per million tokens, for four kinds of tokens: input, output, cache read and cache write. The dashboard adds these up per hour, day and model.

      Example. At $3 per million input tokens and $15 per million output tokens, a message with 20,000 input and 1,000 output costs 0.02 × 3 + 0.001 × 15 = $0.075, before cache prices.
      • It's OpenCode's own estimate, not what GitHub charges. GitHub bills Copilot in credits per request, with its own multipliers per model.
      • It only covers usage that went through OpenCode. Copilot in your editor, the Copilot CLI or the web is counted by GitHub but never shows up here. The "left" figure is always right; per-day and per-model detail can be partial.
      • Some messages are recorded with a cost of 0, for example when OpenCode has no price for a model. Their tokens still count, but their cost doesn't, so local cost can run low. Models and messages with no data at all are dropped.

      5. Calibration factor

      To bring the local estimate closer to what GitHub really charged, the dashboard compares the two over every snapshot interval where both grew:

      factor = portal growth ÷ local cost in the same intervals

      Example. Over a few intervals the quota grew $3.50 (350 cr) while OpenCode logged $2.00. The factor is 3.50 ÷ 2.00 = ×1.75. A new local message of $1.00 is then shown as $1.75.
      • It's applied automatically only once the matched local cost reaches $1.00. Until then the factor is 1 and the Calibration tile shows "—".
      • To fix your own number, set TOKEN_MONITOR_COST_FACTOR. It always wins over the calibration.
      • Limits: a few intervals make a noisy ratio; GitHub's per-model multipliers differ from token prices, so the ratio shifts with your model mix; and usage from other Copilot clients inside an interval pushes portal growth up while local cost stays put. Treat it as a rough scale, not a rate.

      6. Lasts until: when the budget runs out

      The Lasts until line says how long the budget lasts if you keep spending like you have been. Spending per day (the burn rate) is the average daily cost over the last 7 days (including today), taken from the daily costs above. If local usage covers less than half of this period's spend (so it would hide usage from other tools), the dashboard uses the period average instead: spent ÷ days elapsed (at least 1). The tile says which one: "7d avg" or "period avg". The tile shows $ per day, with the credits per day under it; multiply by 100 for credits per day ($4/day = 400 cr/day).

      last until = now + (budget − spent) ÷ spending per day

      Example. Spent $84 of $300, burning $4/day (400 cr/day). Left is $216, so it lasts 216 ÷ 4 = 54 days. With 20 days to the reset, the projected spend at the reset is 84 + 4 × 20 = $164, so the line says "Lasts past the reset (about $136 left on 1 Nov)".
      At $12/day instead: 216 ÷ 12 = 18 days. That is 2 days before the reset, so the line turns red and says "At this pace credits run out ~Wed 28 Oct (in 18d), 2d before the reset" (with your real date).

      Other states: "No recent spending" when nothing was spent lately, and "Budget used up" (red) once spent reaches the budget. In the text output and the desktop app the same sentence is on the row called lasts until.

      7. Most used models

      Per-model cost and tokens are added up over the days in the range you picked, then ranked by Cost or by Tokens (your choice). The top 6 are listed; everything else is grouped as Other (n). The percentage is the model's share of the chosen measure among visible models. Hidden models (Settings) are left out of the shares.

      Model costs are scaled by the calibration factor, and on days with portal spend they are rescaled so the models add up to that day's total. Rankings and shares are more reliable than the absolute amounts: if the factor is off, every model is off by the same amount, so the order and shares hold.

      8. Offline, stale and sample data

      • GitHub unreachable (VPN down, token expired): the dashboard shows the latest saved snapshot plus the local cost since then, adds an amber banner ("offline — last portal data 3h ago"), and marks Spent as an estimate. It goes back to exact numbers as soon as a fetch works.
      • If that snapshot belongs to a billing period that has already ended, it isn't shown, and you'll see an error instead.
      • Sample data: with no token, no gh login and no history, the dashboard shows built-in sample numbers. They are always labelled "MOCK DATA" with a red banner. They are not your usage.
      • The page re-reads data every 60 seconds; the server reuses one fetch for 45 seconds.

      9. Tokens

      The token chart splits each message's tokens into output (including reasoning tokens), input (new, uncached prompt text) and cache (cache reads plus cache writes). The total is the sum of the three.

      Example. One long coding turn: 6,000 input, 1,200 output, 180,000 cache read, 4,000 cache write. Total = 191,200 tokens, and cache is 184,000 of them, 96%.

      Because cache is so large, the dashboard shows the pieces separately. The Input, output and cache tokens card gives the totals for the range you picked, with each part's share of all tokens. Input vs output tokens draws input and output side by side for each day (or hour), on their own scale and without cache, so you can see them. Cache tokens does the same for cache read and cache write. Output includes reasoning tokens. All of this is read from OpenCode's records, so it is a local estimate that leaves out Copilot use in editors or the CLI.

      Example. A day with 150,000 input, 130,000 output, 9,900,000 cache read and 740,000 cache write: cache is 10.64M of 10.92M tokens (97%), yet input and output (280,000) are the part you control with your prompts, and they get their own chart.

      Agent sessions re-send the whole conversation every turn, and most of it comes from the cache. So cache usually dominates the token count. That's normal. Cache tokens are cheap, which is why a huge token total can still be a small cost.

      10. Most used skills

      OpenCode records each time it loads a skill. The dashboard counts those loads per skill name over the range you picked, ranks them (top 8, the rest grouped as Other (n)), and shows each skill's share and when it was last loaded.

      • What is counted: completed skill tool calls in OpenCode's part table, read from the same read-only database as the rest. Only the skill name and the time are read. The skill's text is never read or shown.
      • Provider filter: a load is linked to its message so that only your selected providers count (TOKEN_MONITOR_PROVIDERS). If the message can't be found or has no provider, the load is still counted.
      • Not skipped quietly: rows that aren't skill loads, that failed, that have no name, or that are damaged are ignored one by one; they don't stop the list.
      • It's a count, not a cost. A skill that was loaded often isn't necessarily expensive, and the dashboard doesn't try to work out what a skill cost. Like the model list, this only covers OpenCode. In sample-data mode the list is sample data too.
      Example. In a range where OpenCode loaded caveman 16 times, ponytail 16 times and jira-management 4 times, with nothing else, the shares are 44%, 44% and 11% of 36 loads.

      Chart types

      The Bar / Line / Dots / Pie switch above the charts changes how every chart is drawn. It's remembered in your browser. The numbers behind the charts don't change.

      • Bar, Line, Dots draw one point per day (or per hour on 24h and 72h). In Line and Dots the token chart shows output, input and cache as separate lines, so cache is no longer stacked on top. The cost chart shows one total per day: the portal spend where it is known plus the local estimate for the rest. Hovering still shows the day's details.
      • Pie (a donut) does not show time. It shows how the whole selected range splits up. Tokens per day: output, input, cache read and cache write. Input vs output: input against output. Cache tokens: read against write. Cost per day: cost by model, from the local per-model estimates. The caption on each card says what its pie shows, and the number in the middle is the total of the range.
      • Most used models and skills are rankings, not time series. Bar is the list with bars, Dots draws each as a dot on a line, Pie shows each one's share, and Line falls back to bars because a line isn't meaningful there.

      Because the models are scaled by the calibration factor (see above), a model pie is more reliable for shares than for dollar amounts.

      Hourly charts and the time slice

      The first two charts are Tokens per hour and Cost per hour, built from OpenCode's hourly records (the last 31 days are kept). Hovering an hour shows input, output, cache read, cache write, messages and the top models. The cost chart is in dollars only: OpenCode's estimate times the calibration factor. It's a local estimate, because GitHub's quota isn't split by hour. The 24h / 72h / 7 / 14 / 30 day buttons set how far back the hourly charts go.

      The time slice (From / To boxes under the range buttons, or drag across either hourly chart) picks whole hours, start included and end excluded, and filters every card: both hourly charts, the totals, the input/output/cache charts, most used models and most used skills. Reset (or any range button) clears it. Times outside the loaded hours (the last 31 days) can't be picked: the boxes are limited to that span, and a drag stays inside the chart. The slice works in whole local hours and lives only in this page (it isn't saved or sent anywhere). The per-day charts show the whole days the slice touches, since daily portal spend can't be cut by the hour. The header's budget numbers (spent, left, at this pace) never change with the slice.

      How to set up

      From a fresh checkout to numbers on screen. The dashboard needs your GitHub login (for the quota) and your OpenCode data (for the per-day, per-hour and per-model detail).

      1. Before you start

      • Docker for the web dashboard. Or just python3 (3.10 or newer) if you only want the command line or the GTK app.
      • The GitHub CLI (gh), logged in to your GitHub host. The dashboard borrows its token; it never asks for a password. 
        gh auth login -h github.example.com
      • VPN on. The company GitHub API is only reachable from inside the network.
      • OpenCode installed, and used at least once. Its database is read from ~/.local/share/opencode/opencode.db (read-only).

      2. Quick start

      Web dashboard (Docker). Clone the repo, then from its folder:

      scripts/web-up.sh -d

      Then open http://localhost:8080. The script reads your token from gh, passes it to the container as a variable (never printed or stored in the image) and builds and starts it. Stop it with docker compose down.

      Command line. No install needed:

      python3 bin/token-monitor --text

      GTK desktop app. Needs PyGObject with GTK 4 and libadwaita. Run it from the checkout, or install it with symlinks (./scripts/install.sh --undo removes them again):

      python3 bin/token-monitor
./scripts/install.sh

      Without Docker you can also run the web page yourself: python3 -m token_monitor.web --port 8080. It listens on 127.0.0.1 only.

      3. Configuration

      Every setting is optional. Easiest way: copy the example file and edit it.

      cp .env.example .env && chmod 600 .env

      Settings are looked up in this order, first match wins: 1. real environment variables, 2. the .env file in the repo root, 3. ~/.config/token-monitor/config (same KEY=VALUE format; the Settings drawer writes there), 4. the default.

      NameDefaultWhat it does
      TOKEN_MONITOR_SOURCEautogithub, curl or mock. Auto picks github when a token or a gh login is found, otherwise sample data. Set mock to use sample data on purpose.
      TOKEN_MONITOR_GH_HOSTgithub.comThe GitHub host to ask. For GitHub Enterprise use your host, e.g. github.example.com.
      TOKEN_MONITOR_GH_TOKENemptyA token to use instead of running gh auth token. A secret: keep .env private (mode 600).
      TOKEN_MONITOR_BUDGETunsetA fixed budget, in dollars. It hides the real budget: the dashboard shows this number even if GitHub reports another one. Leave it unset unless the source gives no budget. A value set here shows as read-only in Settings.
      TOKEN_MONITOR_CREDITS_PER_USD100Credits shown as dollars at this rate (30,000 credits = $300). 0 shows raw credits.
      TOKEN_MONITOR_OPENCODE_DB~/.local/share/opencode/opencode.dbPath to OpenCode's database.
      TOKEN_MONITOR_PROVIDERSgithub-copilotWhich OpenCode providers are counted, separated by commas.
      TOKEN_MONITOR_HISTORY_DIR./.token-monitorFolder for history.jsonl (saved snapshots).
      TOKEN_MONITOR_USAGEopencodeWhere local usage comes from: opencode, or mock (the default when the source is mock).
      TOKEN_MONITOR_COST_FACTORunsetMultiplier for OpenCode's cost estimate. Unset = worked out from your history, or 1 until there is enough.
      TOKEN_MONITOR_PORT8080Docker only: the port on this machine. Read by docker-compose, not by the app.
      TZhost's time zone (UTC if unknown)Time zone for the daily and hourly buckets. web-up.sh copies the host's.

      There are more keys for the curl source (TOKEN_MONITOR_CURL_CMD, TOKEN_MONITOR_JSON_MAP, TOKEN_MONITOR_UNIT); see .env.example. That source needs curl inside the container, which the Docker image does not have.

      4. Where data is stored

      • History: .token-monitor/history.jsonl in the repo (ignored by git). Every successful fetch adds a snapshot: only four numbers, nothing secret. The CLI, the GTK app and the container share it.
      • Last good answer: ~/.cache/token-monitor/last-good.json, used when a fetch fails.
      • Docker settings: the tm-data volume (budget override, hidden items). It survives docker compose down; docker compose down -v deletes it. It is separate from your host's ~/.config/token-monitor.
      • OpenCode: your OpenCode folder is mounted read-only into the container (set OPENCODE_DATA_DIR to use another folder). The whole folder is mounted because SQLite's log files must sit next to the database.

      5. Host or bridge network

      Host networking is the default. The container shares your machine's network, so it sees the VPN and can reach the company GitHub API. The page still listens on 127.0.0.1 only.

      Bridge is Docker's isolated network. It does not see the VPN, so the company host is usually unreachable from it; use it only when you don't need that (for example sample data). The port is published on 127.0.0.1.

      scripts/web-up.sh --bridge

      6. When you are offline

      If GitHub can't be reached (VPN down, token expired), the dashboard shows the last saved numbers from the history under an amber banner. If there is no history yet, it shows an error instead. Local OpenCode usage keeps working, since it needs no network.

      Sample data is never silent: when you see a red MOCK DATA banner, the numbers are not yours.

      7. Security

      • There is no login. Anyone who can open the page can read your usage and change its settings.
      • It is bound to 127.0.0.1, so only this machine can open it. Don't expose it to your network, and never to the internet.
      • Your GitHub token is never stored by the app, returned by the API or written to the logs.
      • The OpenCode folder is read-only, but the container can see all of it (including OpenCode's own auth.json, which the app never reads). To avoid that, point OPENCODE_DATA_DIR at a folder holding just a copy of opencode.db.

      8. Troubleshooting

      You seeWhy, and what to do
      Red MOCK DATA bannerNo token reached the app. Run gh auth login -h github.example.com, then start with scripts/web-up.sh (not a bare docker compose up), or set TOKEN_MONITOR_GH_TOKEN in .env.
      401, or a token that expiredRefresh the login, then restart: gh auth refresh -h github.example.com. The container only gets the token when it starts.
      Amber offline bannerGitHub is unreachable. Check that the VPN is on, and that you didn't start with --bridge.
      Empty charts or no modelsThe OpenCode database wasn't found or can't be read. Check TOKEN_MONITOR_OPENCODE_DB (or OPENCODE_DATA_DIR in Docker) and the file's permissions: the container runs as your own user so it can read it.
      Numbers differ from an organisation budget portalThe portal refreshes with a delay, and it is a different figure: this shows your personal seat quota from GitHub. See "How it's calculated".
      Hours look shiftedSet TZ to your time zone.
      Budget doesn't match GitHubA TOKEN_MONITOR_BUDGET override is set (in the environment, .env or Settings). Remove it to show the real one.
